## Registration integrity (critical invariant)

Capacity check + reservation + payment order + webhook + confirm must happen inside DB transactions per `docs/superpowers/specs/2026-09-13-mun-hub-mvp-backend-design.md` Section 3. Never trust client-supplied `userId` in any action that reads/writes a specific user's data — derive actor identity from `getSession()` server-side only (IDOR risk flagged by UI-session review, fixed in Drizzle rewrite).

`initiateRegistration`'s capacity check row-locks the registration product (`.for('update')`) inside the transaction — without this, concurrent registrations for the same product all read the same pre-insert count under Postgres READ COMMITTED and oversell. Covered by a concurrency regression test (`lib/actions/registration.test.ts`, 10 concurrent callers vs capacity 3). The payments webhook only confirms a registration that is still `PAYMENT_PENDING` (never resurrects a TTL-expired/cancelled one) and releases the seat (sets `CANCELLED`) on a failed payment instead of leaving it stuck.

**2026-09-13 follow-up (found by mun-hub-02's adversarial-coach, fixed same day):** the row lock only serialized the capacity count — it did NOT stop the *same* user from holding multiple simultaneous active registrations for one product (double-charge risk). Fixed: `initiateRegistration` now also checks, inside the same locked transaction, whether the caller already has an active (PENDING/PAYMENT_PENDING/CONFIRMED) registration for that product and rejects a second one. Separately, the webhook's `paid` branch used to mark the payment `PAID` unconditionally even if the registration had already expired/been cancelled — money moved but the registration stayed dead, silently orphaning the charge. Fixed: webhook now row-locks the registration, and only marks the payment `PAID` + confirms if the registration is still `PAYMENT_PENDING`; otherwise marks it `REFUNDED` (honest — a refund is owed) and leaves the registration alone. Response body now includes `refundOwed: boolean`. Same missing-row-lock bug existed in `transitionMun` (two admins deciding the same mun concurrently) — fixed with the same `.for('update')` pattern.

A separate, older Cloudflare Worker named `mun-hub` (OpenNext build) also exists at `mun-hub.somapujith.workers.dev` with no custom domain attached — irrelevant leftover, not part of the current architecture.

**Live Cloudflare zone:** `munhub.in`, migrated from BigRock's nameservers to Cloudflare's (`marty.ns.cloudflare.com`/`sima.ns.cloudflare.com`). Two Workers: `munhub-web` (`web/wrangler.jsonc` — `app.`/`organize.`/`admin.munhub.in` as Custom Domains, `*.munhub.in/*` as a Workers Route for per-MUN slug pages) and `munhub-api` (`server/wrangler.jsonc` — `api.munhub.in` as a Custom Domain **plus an explicit `api.munhub.in/*` Workers Route**, backed by Cloudflare Hyperdrive for Neon access). Both required: a Custom Domain does not automatically beat a zone-level wildcard Route for the same hostname — without the explicit Route, `api.munhub.in` was intermittently served by `munhub-web`'s wildcard instead. A Workers Route also does not create its own DNS record the way a Custom Domain does — the wildcard needed a manually-added `*.munhub.in` DNS record (any proxied placeholder) or nothing on it would resolve.

**Critical, easy-to-repeat bug: Cloudflare Workers never populate custom vars/secrets into `process.env` — only `NODE_ENV` is special-cased.** A first deploy pass "fixed" `PAYMENT_FIELD_KEY` by making its module-load lazy (avoided a deploy-time crash) but didn't fix the actual read source, and a separate, unnoticed instance of the same bug meant `COOKIE_DOMAIN` was silently never applied — a real login against production came back with no `Domain=` attribute at all, meaning the entire point of this migration (session shared across `app.`/`organize.`/`admin.munhub.in`) **was not actually working** despite the deploy "succeeding" and all tests/tsc passing. Fixed generically: new `lib/runtime-env.ts` (`setRuntimeEnv`/`getRuntimeEnv`) + `server/middleware/runtime-env.ts`, mirroring the existing `lib/db/hyperdrive-bridge.ts` pattern, bridging `c.env` into it on every request. `server/routes/auth.ts` (cookie domain), `lib/crypto/field-encryption.ts` (payment field key), `lib/payments/mock-adapter.ts` (webhook secret), and `server/src/app.ts`/`server/middleware/csrf.ts`'s CORS origin-allowlist reads all now go through `getRuntimeEnv()`. **Rule going forward: never read a custom env var via `process.env.X` anywhere in `/server` or a `lib/` module it depends on — always `getRuntimeEnv('X')`.** A plain `process.env.X` read passes `tsc`, passes every test, and silently returns `undefined` only once actually deployed — the bug is invisible unless you test the real deployed URL. Verified after the fix: a cookie obtained by logging in via `app.munhub.in` was successfully reused for a session check against `organize.munhub.in`.

Full narrative: `docs/superpowers/specs/2026-09-17-subdomain-architecture-design.md` (§5c has the runtime-env bug in detail), `docs/superpowers/plans/2026-09-17-subdomain-architecture.md`.

The legacy root `@opennextjs/cloudflare` scaffold (`wrangler.jsonc`, `open-next.config.ts`, `cf:preview`/`cf:deploy` npm scripts) is now fully unused — nothing points to it in production. `.dev.vars.example` mirrors `.env.example` for that scaffold's local-secrets convention; it does not cover `/web` or `/server`'s own env vars (see their own `wrangler.jsonc`/README).

A Cloudflare API token was pasted directly into whichever session needed it per the no-relay-between-sessions rule (still correct practice going forward — never relay it). One more non-obvious Cloudflare gotcha from this rollout: a fresh zone's Custom Domains and Workers Routes are gated by **separate** API token permissions — a token can deploy Custom Domains fine while failing on Routes with a generic "Authentication error [code: 10000]" until "Zone → Workers Routes → Edit" is added.

## Test/dev DB isolation (critical, learn from this)

**`.env` points at the team's live Neon instance — tests must NEVER read it.** Vitest loads `.env.test` (committed, safe mock-only values, pinned to local Docker Postgres) via `vitest.setup.ts`, regardless of what `.env` says. This exists because a test suite ran against Neon before this was caught and wrote 472 junk MUNs + 941 junk users into the DB the dev server (and anyone browsing it) reads from — cleaned up once with user confirmation (mass-delete on shared cloud data, correctly blocked by the auto-mode classifier until confirmed). If you ever see `.env.test` deleted or `vitest.setup.ts` pointed back at `.env`, that's a regression — fix it before running tests.

Local Docker Postgres (`docker-compose.yml`, `npm run db:up`) is what tests actually run against. It's accumulated a lot of historical test-run junk data of its own — harmless since nobody browses it, but don't be surprised by hundreds of "Config Mun"/"Test Mun"/etc rows if you inspect it directly.

## Verification & Confirmation Trust Layer (slice 1, landed 2026-09-13)

New PRD: `docs/prd/MUNHub_Organizer_Modules_Verification_Confirmation_PRD.md`. Full design: `docs/superpowers/specs/2026-09-13-verification-trust-layer-design.md`. Implementation plan: `docs/superpowers/plans/2026-09-13-verification-trust-layer.md` (7 tasks, all landed). This is "slice 1" — the core trust mechanism only, applied to modules that already existed (mun details, committees, portfolios, registration products). Registration form builder, QR check-in, results/awards, certificates, communications are deliberately out of scope for this slice (see spec doc Section 6).

**Lifecycle change:** `MunStatus` gained 5 values — `ORGANIZER_CONFIRMATION`, `VERIFIED`, `RESULTS_PENDING`, `RESULTS_UNDER_REVIEW`, `CANCELLED`. The path is now `CONTENT_SUBMITTED → ORGANIZER_CONFIRMATION → VERIFICATION → VERIFIED → PUBLISHED`, not the old `CONTENT_SUBMITTED → VERIFICATION → PUBLISHED`. **`publishMun` now requires `VERIFIED`, not `VERIFICATION`** — a real behavior change, not just a rename. `VERIFIED`/`PUBLISHED`/`REGISTRATION_OPEN` can transition back to `VERIFICATION` (that's the re-verification path). `CANCELLED` is reachable from most non-terminal states.

**New tables** (`lib/db/schema.ts`): `mun_module_verifications` (one row per `(munId, moduleName)`, tracks NOT_SUBMITTED/PENDING_REVIEW/VERIFIED/CHANGES_REQUESTED/REJECTED — module-level, not field-level, per an explicit scoping decision), `verification_issues` (reviewer-recorded findings, severity BLOCKER/HIGH/MEDIUM/LOW, append-only), `organizer_confirmations` (Gate 3 whole-submission confirmation snapshot), `mun_versions` (created only when a mun passes/re-passes VERIFIED). `registrations.munVersionId` was added as a **nullable, unwired** column — schema exists, `initiateRegistration` does not populate it yet, deliberately deferred to a future slice.

**New actions:**
- `lib/lifecycle/module-verification.ts`: `getModuleVerificationState(munId, moduleName)` (lazily creates a NOT_SUBMITTED row), `confirmModule(munId, moduleName, session)` (organizer's per-module "I confirm..." — only legal from NOT_SUBMITTED/CHANGES_REQUESTED), `reviewModule(munId, moduleName, decision, issues[], session)` (OPERATIONS/ADMIN/SUPER_ADMIN, records issues, and if decision is VERIFIED checks `checkAllModulesVerified`), `checkAllModulesVerified(munId, actorId)` (auto-advances the mun to VERIFIED once all 4 tracked modules pass — `actorId` must be a real user id, `verificationLogs.reviewerId` is a NOT NULL FK, a literal `'system'` string would violate it).
- `lib/lifecycle/organizer-confirmation.ts`: `submitFinalConfirmation(munId, session)` — Gate 3, snapshots mun+committees+portfolios+products into `organizer_confirmations`, transitions CONTENT_SUBMITTED→ORGANIZER_CONFIRMATION→VERIFICATION as two separate audit-logged steps.
- `lib/lifecycle/reverification.ts`: `detectHighImpactChange(moduleName, before, after)` (pure function, `HIGH_IMPACT_FIELDS` constant per module — name/dates/venue for mun_details, price/capacity/deadline for registration_products, name/capacity for committees), `triggerReverificationIfNeeded(moduleName, before, after, munId, actorId)` — called from the end of `updateMunDetails`/`updateRegistrationProduct`/`updateCommittee` in `mun-config.ts`; no-op if the mun isn't VERIFIED yet or the change isn't high-impact.
- `lib/actions/admin-review.ts` gained `getModuleReviewQueue()` (all PENDING_REVIEW module rows + mun name, for the Verification Console).

**Compatibility note — `submitMunForVerification` in `mun-config.ts`:** the pre-existing organizer dashboard panel (`app/organizer/dashboard/[munId]/setup/verification-panel.tsx`) called this function assuming `CONTENT_SUBMITTED → VERIFICATION` was a direct transition. It no longer is. `submitMunForVerification` was patched to perform both hops internally (a lighter-weight shim, no confirmation snapshot) so the existing panel keeps working, but it should be replaced by a direct call to `submitFinalConfirmation` once the UI is updated to show the full Gate 3 confirmation summary. `lib/mun-status.ts` and `components/mun/mun-status-badge.tsx` got mechanical placeholder entries for the 5 new MunStatus values (TODO-commented inline) to keep tsc green — these need real copy/icon review from whoever owns UI next, not a design pass from backend.

## Organizer Onboarding & Go-Live Pipeline (landed 2026-09-14, extends the trust-layer slice above — does not replace it)

New PRD: `docs/prd/MUNHub_Organizer_Onboarding_Go_Live_Pipeline_PRD.md`. Full design: `docs/superpowers/specs/2026-09-14-onboarding-go-live-pipeline-design.md`. Implementation plan: `docs/superpowers/plans/2026-09-14-onboarding-go-live-pipeline.md` (13 tasks, all landed). `mun_module_verifications`/`verification_issues`/`organizer_confirmations`/`mun_versions` from the trust-layer slice above are all reused and widened, not duplicated.

**The single most important thing for a future agent not to get wrong — Gate-1 vs Gate-2 vocabulary.** `SUBMITTED`/`UNDER_REVIEW`/`APPROVED`/`CHANGES_REQUESTED` are reused by TWO completely different review gates that happen to share English words:

- **Gate 1** — organizer-application approval ("is this organization allowed to run a MUN on our platform"). Table: `organizerApplications`. Action: `reviewMunApplication` (`lib/actions/admin-review.ts`). Path: `DRAFT → SUBMITTED → UNDER_REVIEW → {APPROVED, REJECTED, CHANGES_REQUESTED}`, `APPROVED → ONBOARDING` (Gate 1 exit). These ARE real `MunStatus` enum values used exactly this way.
- **Gate 2** — MUN-content review ("is this MUN's content correct enough to publish"). The PRD's own vocabulary for this gate is *also* SUBMITTED/UNDER_REVIEW/CHANGES_REQUESTED/APPROVED, but that vocabulary is **deliberately not reused as enum values** — Gate 2 is implemented on differently-named existing content-gate `MunStatus` values instead, so the two gates can never collide in a `mun.status` check: `CONTENT_SUBMITTED` (PRD's content "SUBMITTED"), `AUTOMATED_VALIDATION` (new, no PRD-name collision), `ORGANIZER_CONFIRMATION` (PRD's Gate-3 confirmation), `VERIFICATION` (PRD's content "UNDER_REVIEW"), `VERIFIED` (PRD's content "APPROVED"), `ACTION_REQUIRED` + module-level `CHANGES_REQUESTED` (PRD's content "CHANGES_REQUESTED").

`lib/lifecycle/mun-state-machine.ts`'s `PRD_STATE_ALIASES` maps the four Gate-2 enum values to their PRD display words for UI layers — the DB always stores the real enum value; only the label differs. **`mun.status === 'UNDER_REVIEW'` always means Gate 1, full stop** — `getReviewQueue`'s `inArray(muns.status, ['SUBMITTED','UNDER_REVIEW'])` filter means "organizer applications", never "content submissions". Never route a Gate 2 decision through `reviewMunApplication`, and never route a Gate 1 decision through `reviewSubmission` (`lib/lifecycle/go-live.ts`). If you find yourself wanting to reuse a Gate-1 name for a Gate-2 concept, that is the exact trap this design exists to avoid.

**6 new `MunStatus` values:** `AUTOMATED_VALIDATION`, `GO_LIVE_QUEUE`, `PUBLISHING`, `UNPUBLISHED`, `CONFERENCE_ACTIVE`, `COMPLETED`/`ARCHIVED`/`SUSPENDED` round out the full post-publish lifecycle. Full path: `ONBOARDING ↔ {ACTION_REQUIRED, READY_FOR_SUBMISSION} → CONTENT_SUBMITTED → AUTOMATED_VALIDATION → ORGANIZER_CONFIRMATION → VERIFICATION → {VERIFIED, CHANGES_REQUESTED→ACTION_REQUIRED, REJECTED} → {PUBLISHED, GO_LIVE_QUEUE→PUBLISHING→PUBLISHED} → REGISTRATION_OPEN → REGISTRATION_CLOSED → CONFERENCE_ACTIVE → RESULTS_PENDING → RESULTS_UNDER_REVIEW → COMPLETED → ARCHIVED`. `VERIFIED`/`PUBLISHED`/`UNPUBLISHED`/`REGISTRATION_OPEN`/`REGISTRATION_CLOSED`/`SUSPENDED` can all transition back to `VERIFICATION` (the re-verification path, below). Full transition table lives in `mun-state-machine.ts`'s `ALLOWED_TRANSITIONS` — read its header comment before touching any Gate-1/Gate-2-adjacent status.

**`PUBLISHED` is the PRD's LIVE state, deliberately not renamed.** The PRD calls a live mun "LIVE"; the enum value stays `PUBLISHED` (matches the repo's pre-existing convention, appears in two tables' live Neon data). `LIVE` exists only as a **display label** via `PRD_STATE_ALIASES`/`lib/mun-status.ts` — never add a distinct `LIVE` enum value.

**The 15-module registry.** `lib/lifecycle/module-registry.ts`'s `MODULE_REGISTRY` (15 entries) is the single source of truth for the tracked module keys, their default-required flag, their phase (`CONTENT`/`COMMERCE`/`OPERATIONS`/`FINAL`), and their `validate` function. `TRACKED_MODULES = MODULE_REGISTRY.map(m => m.key)` — never hardcode a shorter module list anywhere else. Validators live in `lib/lifecycle/validators/{content,committees,commerce,operations}.ts`, each a **pure function** (no I/O, no await) over a `MunValidationContext` batch-loaded once by `lib/lifecycle/validation.ts#loadValidationContext` — the whole design point of "one batched read, then 15 pure functions" (don't turn it back into 15 separate DB round-trips). The `munModuleEnum` is 19 values total: the 15 PRD §38 keys plus 4 legacy pre-PRD keys (`mun_details`, `committees`, `portfolios`, `registration_products`) retained for old data, remapped via a dedicated migration (`ADD VALUE` and the remapping `UPDATE` had to be separate migration files — Postgres <15 cannot do both in one transaction).

**The completion-vs-verification two-axis model** on `mun_module_verifications` (one row per `(munId, moduleName)`): `state` (`NOT_SUBMITTED`/`PENDING_REVIEW`/`VERIFIED`/`CHANGES_REQUESTED`/`REJECTED`) is **reviewer-facing** — has MUNHub verified this module? `completionStatus` (`NOT_STARTED`/`IN_PROGRESS`/`ACTION_REQUIRED`/`COMPLETE`/`LOCKED`) is **organizer-facing** — have you filled this in correctly, and is it currently frozen for edits? These are orthogonal and must never be collapsed into one column. `lib/lifecycle/module-completion.ts`'s `onModuleDataChanged` is the single choke point every module-mutation action calls at the end of a successful write — it recomputes both the one module's completion row and the mun's aggregate progress (`recomputeMunProgress`), and is the only code path that writes `completionStatus` (including the `LOCKED` value — see below).

**`mun_submissions` + SLA + publish idempotency.** New table `mun_submissions` (one active row per mun at a time via a partial unique index mirrored by `ACTIVE_SUBMISSION_PREDICATE` in `go-live.ts`) carries the SLA clock (`slaDeadline`, `slaState`, `slaPausedAt`/`slaPausedTotalMs` for the CHANGES_REQUESTED pause), reviewer assignment, and `publishIdempotencyKey`. `submitMunForReview` (organizer-facing, `go-live.ts`) row-locks the mun, runs the full 15-module automated validation engine, and either fails into `ACTION_REQUIRED` (committing the failing checks as `verification_issues`, source `AUTOMATED`) or passes into `ORGANIZER_CONFIRMATION` with a fresh `mun_submissions` row (1 business day SLA). `reviewSubmission` (OPERATIONS/ADMIN/SUPER_ADMIN) is the Gate 2 content-review decision — **never confuse with Gate 1's `reviewMunApplication`**. `publishFromQueue` is the single most consequential write path in the whole system: one transaction, `FOR UPDATE` on the `mun_submissions` row (not the mun row — the submission row carries the idempotency key), re-validates against LIVE data at a stricter `PUBLISH` stage before ever transitioning to `PUBLISHED`, and an idempotent replay (same key, or already `PUBLISHED`) returns the existing result unchanged rather than erroring or re-running.

**Payment write-only encryption rule.** `mun_payment_settings` stores PAN/account-number ciphertext (`lib/crypto/field-encryption.ts`, AES-256-GCM) plus `last4` — the **`PAYMENT_FIELD_KEY` environment variable** (base64-encoded 32 bytes) must be set or the crypto module throws at load time; no hardcoded key, no default fallback. Every select in `lib/actions/payment-settlement.ts` MUST list columns explicitly (`select()` with no argument is banned in that file) — the `MaskedPaymentSettings` return type structurally omits the ciphertext fields so leaking them is a compile error, not a review catch. **There is no decrypt-and-return action anywhere in this codebase** — write-only, pending a real settlement integration.

**LOCKED enforcement (2026-09-14).** While a mun is in one of the "under active review" statuses (`CONTENT_SUBMITTED`, `AUTOMATED_VALIDATION`, `ORGANIZER_CONFIRMATION`, `VERIFICATION`), an ORGANIZER edit to any module with a non-empty `HIGH_IMPACT_FIELDS` list (see re-verification below) is rejected by `assertModuleNotLocked(munId, moduleKey, session)` (`lib/lifecycle/module-completion.ts`) — called at the top of `mun-config.ts`'s committee/portfolio/registration-product/mun-details update actions, `executive-board.ts`, `mun-documents.ts`, `mun-schedule.ts`, `mun-contact.ts`, and `payment-settlement.ts`'s `upsertPaymentSettings`. **Admin/ops edits are always allowed** — a reviewer fixing a typo mid-review is a legitimate workflow. Modules with an empty `HIGH_IMPACT_FIELDS` list (`BRANDING`, `REGISTRATION_FORM`, `FINAL_REVIEW`) stay editable throughout by design. `completionStatus` is materialized to `LOCKED` on the affected module rows for dashboard display via the same `onModuleDataChanged`/`recomputeMunProgress` path, so the lock is never enforcement-only with a stale-looking dashboard. Note: `assertOwnsOrAdmin` (the ownership gate every action calls before `assertModuleNotLocked`) does not include `OPERATIONS`, so in practice an OPERATIONS-role caller is rejected before ever reaching the lock check even though `assertModuleNotLocked` itself does carve OPERATIONS out — a pre-existing scope boundary in `assertOwnsOrAdmin`, not something this slice changed.

**Re-verification extension.** `lib/lifecycle/reverification.ts`'s `HIGH_IMPACT_FIELDS` is now an **exhaustive** `Record<MunModule, string[]>` covering all 19 module keys (a missing key is a compile error, not a silent no-op) — see that file for the exact per-module field lists. `PAYMENT_SETTLEMENT` is the highest-consequence entry: changing bank details on an already-verified mun **also resets `mun_payment_settings.verificationState` to `PENDING`**, atomically with the module state flip (the fraud vector this closes: get approved with a clean account, then swap in a different one). `REGISTRATION_FORM` has a documented structural exception — `detectHighImpactChange` is a pure field diff and cannot see a field deletion or an optional-to-required flip, so `lib/actions/registration-form.ts` calls `forceReverification` directly for those two cases instead of relying on the pure detector.

**Notifications.** `lib/notifications/pipeline-events.ts` (pre-existing from a peer session, do not recreate) defines the `PipelineEvent` union and `notifyPipelineEvent`/`renderPipelineNotification`. `lib/notifications/resolve-recipients.ts` (new) adds the DB-resolution helpers that file doesn't own: `resolveAdminEmails()` (ADMIN/SUPER_ADMIN/OPERATIONS), `resolveMunNotificationContext(munId)` (`{munName, organizerEmail, slug}`), `buildPublicMunUrl(slug)` (matches `app/sitemap.ts`'s URL pattern). Wired into `submitMunForReview` (SUBMISSION_RECEIVED + NEW_SUBMISSION), `reviewSubmission` (APPROVED / CHANGES_REQUESTED / REJECTED — REJECTED reuses the CHANGES_REQUESTED event shape since the union has no dedicated REJECTED variant, documented as a deliberate imperfect fit in `go-live.ts`), `reviewModule`'s CHANGES_REQUESTED decision (MODULE_ACTION_REQUIRED), and `publishFromQueue`'s success/non-replay path (PUBLISHED with a `publicUrl`). Every call fires **after** its triggering transaction commits, never inside it, and is fire-and-forget (delivery failures are caught and logged, never thrown, never silently swallowed without a log line). `SLA_DELAY` is deliberately unwired — needs a scheduler (see deferred list below).

**Deferred (design spec Section 9 — do not build without asking first):** real payment gateway/settlement execution (`mun_payment_settings` is config-only, nothing initiates a payout); payment account verification is manual admin action only, no penny-drop/API call; encryption key rotation (single env-var key, no HSM/KMS); real email delivery (console adapter only); background jobs/schedulers (SLA state is computed on read, SLA *notifications* like `SLA_DELAY`/"approaching" need a scheduler); two-person approval for high-risk admin actions; team & permissions / sub-organizer roles (`mun_team_members`, whole-mun ownership only for now — the single largest deliberate omission); delegation registration mode; `registrations.munVersionId` capture (column exists, nullable, unwired — publish now reliably creates versions, but wiring capture into `initiateRegistration` is a separate future slice); field-level (vs module-level) verification granularity; full LOCKED-coverage across all 15 modules beyond the `HIGH_IMPACT_FIELDS`-non-empty set; the UI for all of this (organizer "Get Your MUN Live" dashboard, verification console, go-live queue screens — backend contract only, consumed via `getMunProgress`/`getModuleReviewQueue`/`getGoLiveQueue`).

13 tasks landed across this slice, 557+ tests passing, tsc clean throughout. Migrations applied to local Docker Postgres; Neon migration pending the next deploy window.

## Real password auth + student onboarding profile (landed 2026-09-17)

Two changes shipped together: (1) the old passwordless mock login (`signIn(email)` — "any seeded email signs you in") is **gone**, replaced with real password auth; (2) a one-time student profile is now required before a student can register for any MUN, so emergency contact/DOB/school/etc. get filled in once instead of every registration.

**Auth.** `users.passwordHash` (nullable — legacy/pre-signup rows only) stores a `scrypt` hash via `lib/auth/password.ts`'s `hashPassword`/`verifyPassword` (Node's built-in `crypto`, no new dependency — same pattern `lib/auth/session.ts` already used for tokens). `lib/actions/auth.ts` now exports `signIn(email, password)` and `signUp(name, email, password)` (self-serve signup is STUDENT-only — organizer accounts still only come from the organizer-application flow); both throw the same generic `'Invalid email or password'` for an unknown email, a wrong password, or an account with no password set at all, so there's no way to enumerate valid emails by response message. `app/signup/` is new; `app/login/` gained a password field. Demo accounts (seeded) all share the password **`munhub-demo`** — shown on the login page and set via `lib/db/seed.ts` (which now backfills `passwordHash` on re-seed for any pre-existing row that has none, same "backfill drifted fields" pattern `seedMun` already used). `lib/auth/mock-adapter.ts` (still unwired to any real call site) was updated to check the password too, so it can't silently regress into a second passwordless path sitting next to the real one. `server/routes/auth.ts` (Hono) got the matching `password` field on `POST /session` plus a new `POST /users` signup route, kept in sync as a contract update even though no Vite/Hono UI consumes it yet.

**Student profile.** New 1:1 table `student_profiles` (`lib/db/schema.ts`) — DOB, grade/year, residential address, transportation need, emergency contact name/phone/relation, past MUN experience (optional), referral code (optional). "Profile complete" has no separate flag — it's `users.phone` + `users.institution` both set AND a `student_profiles` row existing (`lib/actions/student-profile.ts#isProfileComplete`), because `completeStudentProfile` only ever upserts a row with every required column filled in. `app/profile/` (new) is the one-time-fill-then-editable form. `app/register/[slug]/page.tsx` redirects there (`?redirectTo=/register/<slug>`) before rendering the funnel if the profile is incomplete, with a defense-in-depth re-check inside `submitRegistrationAction` (`app/register/[slug]/actions.ts`, new `reason: "profile"` state) for a direct POST that bypasses the page redirect. Deliberately did **not** touch `lib/actions/registration.ts#initiateRegistration` — that function stays generic/untested-for-profile-completeness on purpose, so the ~600 existing tests that call it directly didn't need touching; the gate lives entirely in the Next-app layer.

**Field-key bridge to the existing per-mun form.** The registration funnel already asked most of this per-registration via `DEFAULT_REGISTRATION_FIELDS`/`munFormFields` (`grade_class`, `residential_address`, `transportation`, `date_of_birth`, `emergency_contact_name`, `emergency_contact_phone`, `mun_experience`, `referral_code`). Rather than merging the two systems, `getProfileFormDefaults(session)` maps the profile onto those exact same `fieldKey`s, and `<RegistrationForm>`'s `customFieldValues` state now initializes from that map (new required `profileDefaults` prop) — a returning student's answers pre-fill matching per-mun fields by key, but the organizer's own field config (required/optional/label/choices) for that mun stays fully authoritative and the field stays editable per registration. The hardcoded "Prior MUN experience" input (a separate, older field from the profile system) is pre-filled the same way via a new optional `defaults.experience`.

## Account settings: change password, forgot-password, email preference (landed 2026-09-17)

Extends the auth work above. `/profile` (the onboarding-details page) gained a second, independent "Account & security" section below the existing form — merged onto the same page rather than a separate route, per explicit user direction. New table `password_reset_tokens` and a new `users.emailNotificationsEnabled` boolean (single-column preference, not a generic preferences system — add another column if/when a second preference is needed).

**In-app change password.** `lib/actions/auth.ts#changePassword(currentPassword, newPassword, session)` re-verifies the current password before allowing a change and does **not** invalidate other sessions (the user is actively signed in choosing this themselves). Wired into `/profile` via `changePasswordAction` (`app/profile/actions.ts`) — an inline `useActionState` form, no redirect on success or failure, since it lives alongside the onboarding form rather than owning the whole page.

**Forgot-password recovery.** New `lib/actions/password-reset.ts`: `requestPasswordReset(email, appUrl)` always resolves successfully regardless of whether the email matches an account (no enumeration), and on a match creates a single-use 1-hour token and sends a reset link through the existing mock `consoleNotificationsAdapter` (no real email delivery in this environment — the link prints to the server console). `resetPassword(token, newPassword)` **does** invalidate every session for the account on success (unlike `changePassword`) — a reset implies the old credential may be compromised. ## Cloudflare Hyperdrive bridge for `lib/db/client.ts` (landed 2026-09-17)

`lib/db/client.ts` is framework-agnostic and has no direct access to Hono's `c.env` binding context (Workers only hands you `env` inside a request handler, not at module-import time — and by the time `server/src/worker.ts`'s module graph finishes evaluating at cold start, `lib/db/client.ts` would already have run). Fixed by making `db`'s underlying Postgres client creation **lazy** — deferred to the first real query (first property access on `db`, via a `Proxy`) instead of eager at module-import time — and adding a small indirection layer for Workers to hand it a connection string before that first access happens:

- `lib/db/hyperdrive-bridge.ts` (new): `setHyperdriveConnectionString`/`getHyperdriveConnectionString`, backed by a `globalThis` slot. `lib/db/client.ts` prefers this over `process.env.DATABASE_URL` when set.
- `server/middleware/hyperdrive.ts` (new): a Hono middleware, registered **first** in `server/src/app.ts`'s chain (must run before anything that touches `db`), that reads `c.env?.HYPERDRIVE?.connectionString` and calls `setHyperdriveConnectionString`. Guards `c.env` itself being `undefined` — Hono's `app.request(...)` test helper (used throughout `server/integration/*.test.ts`) calls handlers with no `env` at all, not even `{}`; this is a real footgun, not a hypothetical one — an earlier version of this change without the `c.env?.` guard broke those integration tests.
- Local Node dev (`server/src/index.ts`, `@hono/node-server`) and Vitest are both **unaffected**: neither ever calls `setHyperdriveConnectionString`, so `lib/db/client.ts` falls through to `DATABASE_URL` exactly as before this change, just resolved one tick later (first query, not import). Confirmed via a stashed-vs-changed full-suite diff — same pre-existing flakiness class either way (see below), same single pre-existing `registration-form.test.ts` flake once file-parallelism is disabled, zero new failures.
- `server/wrangler.jsonc` gained a `hyperdrive` binding block with a placeholder `id` and a TODO comment — the user must run `wrangler hyperdrive create` themselves (a live-Cloudflare-resource step, deliberately not run by this change) and paste the resulting id in.

**`db`'s `Proxy` implementation detail worth knowing if you touch this file again:** the `get` trap must distinguish drizzle's own instance properties (e.g. `$client` — the raw postgres-js client, itself a callable tagged-template function with extra methods like `.end()`/`.begin()` attached) from inherited prototype methods (`select`/`insert`/`transaction`/etc., which need `this === <the real drizzle instance>`, not the Proxy). Blindly `.bind()`-ing every function-typed property (the first version of this fix) silently strips `$client`'s extra methods since `Function.prototype.bind` doesn't copy a function's own properties — broke every test's `afterAll(() => db.$client.end())` teardown. Fixed by checking `Object.prototype.hasOwnProperty.call(instance, prop)`: own properties are returned as-is (untouched), only inherited (prototype) methods get bound.

**Full-suite note (not new, but re-confirmed while verifying this change):** running the entire suite with default vitest file-parallelism against local Docker Postgres (`max_connections: 100`) intermittently throws `sorry, too many clients already` across many unrelated test files — reproduced identically on the pre-change baseline via `git stash`, so it's environmental flakiness from connection-pool exhaustion under parallel workers, not a correctness bug in any one change. `npx vitest run --no-file-parallelism` is the reliable way to get a clean signal locally when a run looks suspicious.
