## Registration integrity (critical invariant)

Capacity check + reservation + payment order + webhook + confirm must happen inside DB transactions per `docs/superpowers/specs/2026-09-13-mun-hub-mvp-backend-design.md` Section 3. Never trust client-supplied `userId` in any action that reads/writes a specific user's data — derive actor identity from `getSession()` server-side only (IDOR risk flagged by UI-session review, fixed in Drizzle rewrite).

`initiateRegistration`'s capacity check row-locks the registration product (`.for('update')`) inside the transaction — without this, concurrent registrations for the same product all read the same pre-insert count under Postgres READ COMMITTED and oversell. Covered by a concurrency regression test (`lib/actions/registration.test.ts`, 10 concurrent callers vs capacity 3). The payments webhook only confirms a registration that is still `PAYMENT_PENDING` (never resurrects a TTL-expired/cancelled one) and releases the seat (sets `CANCELLED`) on a failed payment instead of leaving it stuck.

**2026-09-13 follow-up (found by mun-hub-02's adversarial-coach, fixed same day):** the row lock only serialized the capacity count — it did NOT stop the *same* user from holding multiple simultaneous active registrations for one product (double-charge risk). Fixed: `initiateRegistration` now also checks, inside the same locked transaction, whether the caller already has an active (PENDING/PAYMENT_PENDING/CONFIRMED) registration for that product and rejects a second one. Separately, the webhook's `paid` branch used to mark the payment `PAID` unconditionally even if the registration had already expired/been cancelled — money moved but the registration stayed dead, silently orphaning the charge. Fixed: webhook now row-locks the registration, and only marks the payment `PAID` + confirms if the registration is still `PAYMENT_PENDING`; otherwise marks it `REFUNDED` (honest — a refund is owed) and leaves the registration alone. Response body now includes `refundOwed: boolean`. Same missing-row-lock bug existed in `transitionMun` (two admins deciding the same mun concurrently) — fixed with the same `.for('update')` pattern.

The old `/app` Next.js pages still exist in the repo but are dead code reachable by nothing in production — do not add new work there, and treat any reference elsewhere in this file to "Next.js still primary until Phase 7" as superseded by this line. A separate, older Cloudflare Worker named `mun-hub` (OpenNext build) also exists at `mun-hub.somapujith.workers.dev` with no custom domain attached — irrelevant leftover, not part of the current architecture.

**Live Cloudflare zone:** `munhub.in`, migrated from BigRock's nameservers to Cloudflare's (`marty.ns.cloudflare.com`/`sima.ns.cloudflare.com`). Two Workers: `munhub-web` (`web/wrangler.jsonc` — `app.`/`organize.`/`admin.munhub.in` as Custom Domains, `*.munhub.in/*` as a Workers Route for per-MUN slug pages) and `munhub-api` (`server/wrangler.jsonc` — `api.munhub.in` as a Custom Domain **plus an explicit `api.munhub.in/*` Workers Route**, backed by Cloudflare Hyperdrive for Neon access). Both required: a Custom Domain does not automatically beat a zone-level wildcard Route for the same hostname — without the explicit Route, `api.munhub.in` was intermittently served by `munhub-web`'s wildcard instead. A Workers Route also does not create its own DNS record the way a Custom Domain does — the wildcard needed a manually-added `*.munhub.in` DNS record (any proxied placeholder) or nothing on it would resolve.

**Critical, easy-to-repeat bug: Cloudflare Workers never populate custom vars/secrets into `process.env` — only `NODE_ENV` is special-cased.** A first deploy pass "fixed" `PAYMENT_FIELD_KEY` by making its module-load lazy (avoided a deploy-time crash) but didn't fix the actual read source, and a separate, unnoticed instance of the same bug meant `COOKIE_DOMAIN` was silently never applied — a real login against production came back with no `Domain=` attribute at all, meaning the entire point of this migration (session shared across `app.`/`organize.`/`admin.munhub.in`) **was not actually working** despite the deploy "succeeding" and all tests/tsc passing. Fixed generically: new `lib/runtime-env.ts` (`setRuntimeEnv`/`getRuntimeEnv`) + `server/middleware/runtime-env.ts`, mirroring the existing `lib/db/hyperdrive-bridge.ts` pattern, bridging `c.env` into it on every request. `server/routes/auth.ts` (cookie domain), `lib/crypto/field-encryption.ts` (payment field key), `lib/payments/mock-adapter.ts` (webhook secret), and `server/src/app.ts`/`server/middleware/csrf.ts`'s CORS origin-allowlist reads all now go through `getRuntimeEnv()`. **Rule going forward: never read a custom env var via `process.env.X` anywhere in `/server` or a `lib/` module it depends on — always `getRuntimeEnv('X')`.** A plain `process.env.X` read passes `tsc`, passes every test, and silently returns `undefined` only once actually deployed — the bug is invisible unless you test the real deployed URL. Verified after the fix: a cookie obtained by logging in via `app.munhub.in` was successfully reused for a session check against `organize.munhub.in`.

**Second critical bug, more severe: every DB-backed endpoint intermittently 500'd (~50% of requests) in production.** Root cause: `lib/db/client.ts` cached its Postgres/drizzle client at module scope — correct for a long-lived Node process, but wrong on Cloudflare Workers, which ties I/O objects (a Hyperdrive-backed socket included) to the specific request that created them. A reused Worker isolate (the normal case) or genuinely concurrent requests both hit "Cannot perform I/O on behalf of a different request." (A first attempted fix — `{ prepare: false }` for Hyperdrive's known prepared-statement incompatibility — was real and harmless but did NOT fix this; keep it, but it wasn't the cause.) Fixed by rebuilding `lib/db/hyperdrive-bridge.ts` around `node:async_hooks`'s `AsyncLocalStorage`: `server/middleware/hyperdrive.ts` now runs the rest of the request *inside* `runWithHyperdriveConnectionString(...)`'s scope, and `lib/db/client.ts` builds a fresh client once per request (cached only for that request's async scope), never reusing one across requests. Local Node dev/tests are unaffected — they never enter the ALS scope, so the original process-lifetime cache still applies there. Verified against production: 50/50 sequential and 20/20 concurrent requests to the previously-flaky endpoint all returned 200. **Lesson, bigger than this one bug: a clean `tsc`, a full green test suite, and even a successful `wrangler deploy` prove nothing about this failure mode — it only appears under real Workers traffic patterns (isolate reuse, concurrency) that local dev and Vitest structurally cannot exercise. Never cache a Workers I/O-backed resource at module scope; scope it to the request via `AsyncLocalStorage`.**

Full narrative: `docs/superpowers/specs/2026-09-17-subdomain-architecture-design.md` (§5c has the runtime-env bug in detail), `docs/superpowers/plans/2026-09-17-subdomain-architecture.md`.

The legacy root `@opennextjs/cloudflare` scaffold (`wrangler.jsonc`, `open-next.config.ts`, `cf:preview`/`cf:deploy` npm scripts) is now fully unused — nothing points to it in production. `.dev.vars.example` mirrors `.env.example` for that scaffold's local-secrets convention; it does not cover `/web` or `/server`'s own env vars (see their own `wrangler.jsonc`/README).

A Cloudflare API token was pasted directly into whichever session needed it per the no-relay-between-sessions rule (still correct practice going forward — never relay it). One more non-obvious Cloudflare gotcha from this rollout: a fresh zone's Custom Domains and Workers Routes are gated by **separate** API token permissions — a token can deploy Custom Domains fine while failing on Routes with a generic "Authentication error [code: 10000]" until "Zone → Workers Routes → Edit" is added.

## Test/dev DB isolation (critical, learn from this)

**Tests must NEVER read whatever database `.env` points at — they get their own dedicated database, `mun_hub_test`.** Vitest loads `.env.test` (committed, safe mock-only values) via `vitest.setup.ts`, pinned to `postgresql://mun_hub:mun_hub_dev@localhost:5432/mun_hub_test` on the same local Docker Postgres container as dev, regardless of what `.env` says. This exists because a test suite ran against Neon before this was caught and wrote 472 junk MUNs + 941 junk users into the DB the dev server (and anyone browsing it) reads from — cleaned up once with user confirmation (mass-delete on shared cloud data, correctly blocked by the auto-mode classifier until confirmed).

**2026-09-19 regression, found and fixed:** the original fix pinned `.env.test` to "local Docker Postgres" — but `.env` pointing at local Docker's `mun_hub` database instead of Neon is *also* a documented, supported fallback (see the Neon bullet under Stack above), and at some point `.env` got repointed there. Both files then resolved to the literal same database (`mun_hub` on `localhost:5432`), which defeated the isolation entirely: two days of `vitest` runs against the real `lib/**/*.test.ts` integration suite wrote permanently into the same DB the dev server reads from, undetected until a direct query found 111,290 `users` rows and 44,677 `muns` rows (only 9 real). "Pin `.env.test` to local Docker" was never sufficient — it has to be a database `.env` can't also legitimately point at. Fixed by giving tests their own database name, `mun_hub_test`, created via `docker exec mun-hub-db-1 psql -U mun_hub -d mun_hub -c "CREATE DATABASE mun_hub_test;"` on the existing container and auto-created on any fresh checkout via a Postgres init script (`scripts/docker-init/create-test-db.sql`, bind-mounted in `docker-compose.yml`'s `db` service — `docker-entrypoint-initdb.d/*` scripts only run once, on first initialization of an empty data directory, so this doesn't touch the already-running container's existing data). The junk rows in `mun_hub` itself were left alone (separate cleanup).

Local Docker Postgres (`docker-compose.yml`, `npm run db:up`) hosts both databases: `mun_hub` (dev, and wherever `.env` points when not on Neon) and `mun_hub_test` (tests only). `mun_hub` has accumulated a lot of historical test-run junk data of its own from the incident above — harmless since nobody browses it, but don't be surprised by hundreds of "Config Mun"/"Test Mun"/etc rows, or 6-figure row counts, if you inspect it directly; that cleanup is tracked separately. If you ever see `.env.test` deleted, `vitest.setup.ts` pointed back at `.env`, or **`.env.test`'s `DATABASE_URL` pointing at the same database name as `.env`'s** (Docker or otherwise), that's a regression — fix it before running tests.

**Lifecycle change:** `MunStatus` gained 5 values — `ORGANIZER_CONFIRMATION`, `VERIFIED`, `RESULTS_PENDING`, `RESULTS_UNDER_REVIEW`, `CANCELLED`. The path is now `CONTENT_SUBMITTED → ORGANIZER_CONFIRMATION → VERIFICATION → VERIFIED → PUBLISHED`, not the old `CONTENT_SUBMITTED → VERIFICATION → PUBLISHED`. **`publishMun` now requires `VERIFIED`, not `VERIFICATION`** — a real behavior change, not just a rename. `VERIFIED`/`PUBLISHED`/`REGISTRATION_OPEN` can transition back to `VERIFICATION` (that's the re-verification path). `CANCELLED` is reachable from most non-terminal states.

**New tables** (`lib/db/schema.ts`): `mun_module_verifications` (one row per `(munId, moduleName)`, tracks NOT_SUBMITTED/PENDING_REVIEW/VERIFIED/CHANGES_REQUESTED/REJECTED — module-level, not field-level, per an explicit scoping decision), `verification_issues` (reviewer-recorded findings, severity BLOCKER/HIGH/MEDIUM/LOW, append-only), `organizer_confirmations` (Gate 3 whole-submission confirmation snapshot), `mun_versions` (created only when a mun passes/re-passes VERIFIED). `registrations.munVersionId` was added as a **nullable, unwired** column — schema exists, `initiateRegistration` does not populate it yet, deliberately deferred to a future slice.

**New actions:**
- `lib/lifecycle/module-verification.ts`: `getModuleVerificationState(munId, moduleName)` (lazily creates a NOT_SUBMITTED row), `confirmModule(munId, moduleName, session)` (organizer's per-module "I confirm..." — only legal from NOT_SUBMITTED/CHANGES_REQUESTED), `reviewModule(munId, moduleName, decision, issues[], session)` (OPERATIONS/ADMIN/SUPER_ADMIN, records issues, and if decision is VERIFIED checks `checkAllModulesVerified`), `checkAllModulesVerified(munId, actorId)` (auto-advances the mun to VERIFIED once all 4 tracked modules pass — `actorId` must be a real user id, `verificationLogs.reviewerId` is a NOT NULL FK, a literal `'system'` string would violate it).
- `lib/lifecycle/organizer-confirmation.ts`: `submitFinalConfirmation(munId, session)` — Gate 3, snapshots mun+committees+portfolios+products into `organizer_confirmations`, transitions CONTENT_SUBMITTED→ORGANIZER_CONFIRMATION→VERIFICATION as two separate audit-logged steps.
- `lib/lifecycle/reverification.ts`: **superseded 2026-09-19 — re-verification was removed** (see "No re-verification after VERIFIED" below). The file now only holds `HIGH_IMPACT_FIELDS` / `isHighImpactModule`, which decide which modules are LOCKED during the first review. `detectHighImpactChange`, `triggerReverificationIfNeeded` and `forceReverification` no longer exist.
- `lib/actions/admin-review.ts` gained `getModuleReviewQueue()` (all PENDING_REVIEW module rows + mun name, for the Verification Console).

## Organizer Onboarding & Go-Live Pipeline (landed 2026-09-14, extends the trust-layer slice above — does not replace it)

New PRD: `docs/prd/MUNHub_Organizer_Onboarding_Go_Live_Pipeline_PRD.md`. Full design: `docs/superpowers/specs/2026-09-14-onboarding-go-live-pipeline-design.md`. Implementation plan: `docs/superpowers/plans/2026-09-14-onboarding-go-live-pipeline.md` (13 tasks, all landed). `mun_module_verifications`/`verification_issues`/`organizer_confirmations`/`mun_versions` from the trust-layer slice above are all reused and widened, not duplicated.

**The single most important thing for a future agent not to get wrong — Gate-1 vs Gate-2 vocabulary.** `SUBMITTED`/`UNDER_REVIEW`/`APPROVED`/`CHANGES_REQUESTED` are reused by TWO completely different review gates that happen to share English words:

- **Gate 1** — organizer-application approval ("is this organization allowed to run a MUN on our platform"). Table: `organizerApplications`. Action: `reviewMunApplication` (`lib/actions/admin-review.ts`). Path: `DRAFT → SUBMITTED → UNDER_REVIEW → {APPROVED, REJECTED, CHANGES_REQUESTED}`, `APPROVED → ONBOARDING` (Gate 1 exit). These ARE real `MunStatus` enum values used exactly this way.
- **Gate 2** — MUN-content review ("is this MUN's content correct enough to publish"). The PRD's own vocabulary for this gate is *also* SUBMITTED/UNDER_REVIEW/CHANGES_REQUESTED/APPROVED, but that vocabulary is **deliberately not reused as enum values** — Gate 2 is implemented on differently-named existing content-gate `MunStatus` values instead, so the two gates can never collide in a `mun.status` check: `CONTENT_SUBMITTED` (PRD's content "SUBMITTED"), `AUTOMATED_VALIDATION` (new, no PRD-name collision), `ORGANIZER_CONFIRMATION` (PRD's Gate-3 confirmation), `VERIFICATION` (PRD's content "UNDER_REVIEW"), `VERIFIED` (PRD's content "APPROVED"), `ACTION_REQUIRED` + module-level `CHANGES_REQUESTED` (PRD's content "CHANGES_REQUESTED").

`lib/lifecycle/mun-state-machine.ts`'s `PRD_STATE_ALIASES` maps the four Gate-2 enum values to their PRD display words for UI layers — the DB always stores the real enum value; only the label differs. **`mun.status === 'UNDER_REVIEW'` always means Gate 1, full stop** — `getReviewQueue`'s `inArray(muns.status, ['SUBMITTED','UNDER_REVIEW'])` filter means "organizer applications", never "content submissions". Never route a Gate 2 decision through `reviewMunApplication`, and never route a Gate 1 decision through `reviewSubmission` (`lib/lifecycle/go-live.ts`). If you find yourself wanting to reuse a Gate-1 name for a Gate-2 concept, that is the exact trap this design exists to avoid.

**6 new `MunStatus` values:** `AUTOMATED_VALIDATION`, `GO_LIVE_QUEUE`, `PUBLISHING`, `UNPUBLISHED`, `CONFERENCE_ACTIVE`, `COMPLETED`/`ARCHIVED`/`SUSPENDED` round out the full post-publish lifecycle. Full path: `ONBOARDING ↔ {ACTION_REQUIRED, READY_FOR_SUBMISSION} → CONTENT_SUBMITTED → AUTOMATED_VALIDATION → ORGANIZER_CONFIRMATION → VERIFICATION → {VERIFIED, CHANGES_REQUESTED→ACTION_REQUIRED, REJECTED} → {PUBLISHED, GO_LIVE_QUEUE→PUBLISHING→PUBLISHED} → REGISTRATION_OPEN → REGISTRATION_CLOSED → CONFERENCE_ACTIVE → RESULTS_PENDING → RESULTS_UNDER_REVIEW → COMPLETED → ARCHIVED`. `VERIFIED`/`PUBLISHED`/`UNPUBLISHED`/`REGISTRATION_OPEN`/`REGISTRATION_CLOSED`/`SUSPENDED` still have an edge back to `VERIFICATION`, but organizer edits no longer take it — only a deliberate admin action does (e.g. `reinstateMun`; see "No re-verification after VERIFIED" below). Full transition table lives in `mun-state-machine.ts`'s `ALLOWED_TRANSITIONS` — read its header comment before touching any Gate-1/Gate-2-adjacent status.

**`PUBLISHED` is the PRD's LIVE state, deliberately not renamed.** The PRD calls a live mun "LIVE"; the enum value stays `PUBLISHED` (matches the repo's pre-existing convention, appears in two tables' live Neon data). `LIVE` exists only as a **display label** via `PRD_STATE_ALIASES`/`lib/mun-status.ts` — never add a distinct `LIVE` enum value.

**The 15-module registry.** `lib/lifecycle/module-registry.ts`'s `MODULE_REGISTRY` (15 entries) is the single source of truth for the tracked module keys, their default-required flag, their phase (`CONTENT`/`COMMERCE`/`OPERATIONS`/`FINAL`), and their `validate` function. `TRACKED_MODULES = MODULE_REGISTRY.map(m => m.key)` — never hardcode a shorter module list anywhere else. Validators live in `lib/lifecycle/validators/{content,committees,commerce,operations}.ts`, each a **pure function** (no I/O, no await) over a `MunValidationContext` batch-loaded once by `lib/lifecycle/validation.ts#loadValidationContext` — the whole design point of "one batched read, then 15 pure functions" (don't turn it back into 15 separate DB round-trips). The `munModuleEnum` is 19 values total: the 15 PRD §38 keys plus 4 legacy pre-PRD keys (`mun_details`, `committees`, `portfolios`, `registration_products`) retained for old data, remapped via a dedicated migration (`ADD VALUE` and the remapping `UPDATE` had to be separate migration files — Postgres <15 cannot do both in one transaction).

**The completion-vs-verification two-axis model** on `mun_module_verifications` (one row per `(munId, moduleName)`): `state` (`NOT_SUBMITTED`/`PENDING_REVIEW`/`VERIFIED`/`CHANGES_REQUESTED`/`REJECTED`) is **reviewer-facing** — has MUNHub verified this module? `completionStatus` (`NOT_STARTED`/`IN_PROGRESS`/`ACTION_REQUIRED`/`COMPLETE`/`LOCKED`) is **organizer-facing** — have you filled this in correctly, and is it currently frozen for edits? These are orthogonal and must never be collapsed into one column. `lib/lifecycle/module-completion.ts`'s `onModuleDataChanged` is the single choke point every module-mutation action calls at the end of a successful write — it recomputes both the one module's completion row and the mun's aggregate progress (`recomputeMunProgress`), and is the only code path that writes `completionStatus` (including the `LOCKED` value — see below).

**`mun_submissions` + SLA + publish idempotency.** New table `mun_submissions` (one active row per mun at a time via a partial unique index mirrored by `ACTIVE_SUBMISSION_PREDICATE` in `go-live.ts`) carries the SLA clock (`slaDeadline`, `slaState`, `slaPausedAt`/`slaPausedTotalMs` for the CHANGES_REQUESTED pause), reviewer assignment, and `publishIdempotencyKey`. `submitMunForReview` (organizer-facing, `go-live.ts`) row-locks the mun, runs the full 15-module automated validation engine, and either fails into `ACTION_REQUIRED` (committing the failing checks as `verification_issues`, source `AUTOMATED`) or passes into `ORGANIZER_CONFIRMATION` with a fresh `mun_submissions` row (1 business day SLA). `reviewSubmission` (OPERATIONS/ADMIN/SUPER_ADMIN) is the Gate 2 content-review decision — **never confuse with Gate 1's `reviewMunApplication`**. `publishFromQueue` is the single most consequential write path in the whole system: one transaction, `FOR UPDATE` on the `mun_submissions` row (not the mun row — the submission row carries the idempotency key), re-validates against LIVE data at a stricter `PUBLISH` stage before ever transitioning to `PUBLISHED`, and an idempotent replay (same key, or already `PUBLISHED`) returns the existing result unchanged rather than erroring or re-running.

**Payment write-only encryption rule.** `mun_payment_settings` stores PAN/account-number ciphertext (`lib/crypto/field-encryption.ts`, AES-256-GCM) plus `last4` — the **`PAYMENT_FIELD_KEY` environment variable** (base64-encoded 32 bytes) must be set or the crypto module throws at load time; no hardcoded key, no default fallback. Every select in `lib/actions/payment-settlement.ts` MUST list columns explicitly (`select()` with no argument is banned in that file) — the `MaskedPaymentSettings` return type structurally omits the ciphertext fields so leaking them is a compile error, not a review catch. **There is no decrypt-and-return action anywhere in this codebase** — write-only, pending a real settlement integration.

**LOCKED enforcement (2026-09-14).** While a mun is in one of the "under active review" statuses (`CONTENT_SUBMITTED`, `AUTOMATED_VALIDATION`, `ORGANIZER_CONFIRMATION`, `VERIFICATION`), an ORGANIZER edit to any module with a non-empty `HIGH_IMPACT_FIELDS` list (see re-verification below) is rejected by `assertModuleNotLocked(munId, moduleKey, session)` (`lib/lifecycle/module-completion.ts`) — called at the top of `mun-config.ts`'s committee/portfolio/registration-product/mun-details update actions, `executive-board.ts`, `mun-documents.ts`, `mun-schedule.ts`, `mun-contact.ts`, and `payment-settlement.ts`'s `upsertPaymentSettings`. **Admin/ops edits are always allowed** — a reviewer fixing a typo mid-review is a legitimate workflow. Modules with an empty `HIGH_IMPACT_FIELDS` list (`BRANDING`, `REGISTRATION_FORM`, `FINAL_REVIEW`) stay editable throughout by design. `completionStatus` is materialized to `LOCKED` on the affected module rows for dashboard display via the same `onModuleDataChanged`/`recomputeMunProgress` path, so the lock is never enforcement-only with a stale-looking dashboard. Note: `assertOwnsOrAdmin` (the ownership gate every action calls before `assertModuleNotLocked`) does not include `OPERATIONS`, so in practice an OPERATIONS-role caller is rejected before ever reaching the lock check even though `assertModuleNotLocked` itself does carve OPERATIONS out — a pre-existing scope boundary in `assertOwnsOrAdmin`, not something this slice changed.

**No re-verification after VERIFIED (user decision, 2026-09-19 — do not re-add without asking).** Once a MUN has been verified, organizers can change anything on it (dates, venue, prices, committees, documents, form fields) and it stays live: no status change, no module flip to `PENDING_REVIEW`, no marketplace takeover. This replaced the earlier "high-impact edit sends the MUN back to `VERIFICATION`" flow. Removed: `triggerReverificationIfNeeded`/`forceReverification`/`detectHighImpactChange` and every call site (`mun-config`, `accommodation`, `executive-board`, `mun-schedule`, `mun-contact`, `mun-documents`, `registration-form`, `payment-settlement`). LOCKED-during-first-review is unchanged and still uses `HIGH_IMPACT_FIELDS` (exhaustive `Record<MunModule, string[]>`, a missing key is a compile error). **One deliberate exception, payout only:** `upsertPaymentSettings` still resets `mun_payment_settings.verificationState` to `PENDING` when the bank account changes (the fraud vector: get approved with a clean account, then swap it), and `open-registration` still requires `VERIFIED` payout. It never takes the MUN offline. Public copy (Curation Standards, About, Terms, organizer Setup page) was updated to match; the Terms sentence "Important changes after publication go back through review" was removed and needs the pending legal review.

**Notifications.** `lib/notifications/pipeline-events.ts` (pre-existing from a peer session, do not recreate) defines the `PipelineEvent` union and `notifyPipelineEvent`/`renderPipelineNotification`. `lib/notifications/resolve-recipients.ts` (new) adds the DB-resolution helpers that file doesn't own: `resolveAdminEmails()` (ADMIN/SUPER_ADMIN/OPERATIONS), `resolveMunNotificationContext(munId)` (`{munName, organizerEmail, slug}`), `buildPublicMunUrl(slug)` (matches `app/sitemap.ts`'s URL pattern). Wired into `submitMunForReview` (SUBMISSION_RECEIVED + NEW_SUBMISSION), `reviewSubmission` (APPROVED / CHANGES_REQUESTED / REJECTED — REJECTED reuses the CHANGES_REQUESTED event shape since the union has no dedicated REJECTED variant, documented as a deliberate imperfect fit in `go-live.ts`), `reviewModule`'s CHANGES_REQUESTED decision (MODULE_ACTION_REQUIRED), and `publishFromQueue`'s success/non-replay path (PUBLISHED with a `publicUrl`). Every call fires **after** its triggering transaction commits, never inside it, and is fire-and-forget (delivery failures are caught and logged, never thrown, never silently swallowed without a log line). `SLA_DELAY` is deliberately unwired — needs a scheduler (see deferred list below).

**Deferred (design spec Section 9 — do not build without asking first):** real payment gateway/settlement execution (`mun_payment_settings` is config-only, nothing initiates a payout); payment account verification is manual admin action only, no penny-drop/API call; encryption key rotation (single env-var key, no HSM/KMS); real email delivery (console adapter only); background jobs/schedulers (SLA state is computed on read, SLA *notifications* like `SLA_DELAY`/"approaching" need a scheduler); two-person approval for high-risk admin actions; team & permissions / sub-organizer roles (`mun_team_members`, whole-mun ownership only for now — the single largest deliberate omission); delegation registration mode; `registrations.munVersionId` capture (column exists, nullable, unwired — publish now reliably creates versions, but wiring capture into `initiateRegistration` is a separate future slice); field-level (vs module-level) verification granularity; full LOCKED-coverage across all 15 modules beyond the `HIGH_IMPACT_FIELDS`-non-empty set; the UI for all of this (organizer "Get Your MUN Live" dashboard, verification console, go-live queue screens — backend contract only, consumed via `getMunProgress`/`getModuleReviewQueue`/`getGoLiveQueue`).

13 tasks landed across this slice, 557+ tests passing, tsc clean throughout. Migrations applied to local Docker Postgres; Neon migration pending the next deploy window.

## Organizer email-code sign-in (landed 2026-09-17, explicit user direction)

**Organizers have no password.** publish.munhub.in's `/organizer/login` asks for an email and then a 6-digit code emailed to it. `/organizer/signup` asks for name, email, optional phone and Terms/Privacy consent first, then the code confirms the email, and only then is the account created. Delegate (`/login`, `/signup`) and admin sign-in still use passwords; that scope was the user's choice.

- **Backend:** `lib/actions/organizer-otp.ts` exports `requestOrganizerLoginCode` and `verifyOrganizerLoginCode`.
  - Routes: `POST /api/v1/auth/organizers/code` `{email}` returns 204. `POST /api/v1/auth/organizers/session` takes `{email, code, profile?}`.
  - A verify for an address with no account and no `profile` returns `{status: 'PROFILE_REQUIRED'}` without using up the code. The login page then asks for the details and calls again with the same code. Signup sends `profile` on the first verify.
  - The old password route `POST /auth/organizers` and `signUpOrganizer` are gone.
- **Table `email_login_codes`** (migration `0026`) is keyed by email, not user, because a code also verifies an address with no account yet.
  - Codes are scrypt-hashed with `lib/auth/password.ts#hashPassword`, and verified with `verifyPassword`. To seed a known code in tests, insert `{email, codeHash: await hashPassword('123456'), expiresAt}`.
  - Only the newest unconsumed row per email is valid; requesting a new code consumes the older ones.
  - Limits: 10-minute expiry, single use, 5 wrong guesses lock the code, 60-second resend cooldown, 5 codes per address per hour.
  - Route rate limits in `server/middleware/rate-limit.ts` are keyed per IP plus email, plus 30 code requests per IP per minute.
- **No enumeration, separate accounts:**
  - A code request answers identically for every address.
  - An address that belongs to a delegate or staff account gets an explanatory email and never a usable code. It still gets a throttle row, so the endpoint can't flood that inbox.
  - Account lookups compare `lower(users.email)`.
- **Email:** sent through `getNotificationsAdapter()` using mun-hub-4b's branded template, `lib/notifications/templates/otp-email.ts`.
  - Production sends real mail through ZeptoMail from `noreply@munhub.in`.
  - Locally, and in tests, the console adapter prints the code in the API log line `[notification] <email> …`.
- **Password sign-in still works for any account that has a password**, including seeded demo organizers and E2E fixtures, through `POST /auth/session`. Organizers created by the code flow have `passwordHash = null`, so they can only use codes.
- **Web:** `web/src/components/auth/organizer-otp-form.tsx` (`mode: 'login' | 'signup'`), rendered by `organizer-login-page.tsx` and `organizer-signup-page.tsx` inside the shared `OrganizerAuthLayout`.
- **Destination after sign-in:**
  - A new organizer account lands on `/organizer/welcome` (`organizer-welcome-page.tsx`): a District-style three-step page whose "Start your journey" button leads to `/organizer/apply`. The user asked for that page to stay bright, so it uses fixed light colors instead of theme tokens and must look the same in dark mode.
  - Returning organizers go to `/organizer/dashboard`.
  - An explicit `?redirectTo=` wins over both.

## Cloudflare Hyperdrive bridge for `lib/db/client.ts` (landed 2026-09-17)

`lib/db/client.ts` is framework-agnostic and has no direct access to Hono's `c.env` binding context (Workers only hands you `env` inside a request handler, not at module-import time — and by the time `server/src/worker.ts`'s module graph finishes evaluating at cold start, `lib/db/client.ts` would already have run). Fixed by making `db`'s underlying Postgres client creation **lazy** — deferred to the first real query (first property access on `db`, via a `Proxy`) instead of eager at module-import time — and adding a small indirection layer for Workers to hand it a connection string before that first access happens:

- `lib/db/hyperdrive-bridge.ts` (new): `setHyperdriveConnectionString`/`getHyperdriveConnectionString`, backed by a `globalThis` slot. `lib/db/client.ts` prefers this over `process.env.DATABASE_URL` when set.
- `server/middleware/hyperdrive.ts` (new): a Hono middleware, registered **first** in `server/src/app.ts`'s chain (must run before anything that touches `db`), that reads `c.env?.HYPERDRIVE?.connectionString` and calls `setHyperdriveConnectionString`. Guards `c.env` itself being `undefined` — Hono's `app.request(...)` test helper (used throughout `server/integration/*.test.ts`) calls handlers with no `env` at all, not even `{}`; this is a real footgun, not a hypothetical one — an earlier version of this change without the `c.env?.` guard broke those integration tests.
- Local Node dev (`server/src/index.ts`, `@hono/node-server`) and Vitest are both **unaffected**: neither ever calls `setHyperdriveConnectionString`, so `lib/db/client.ts` falls through to `DATABASE_URL` exactly as before this change, just resolved one tick later (first query, not import). Confirmed via a stashed-vs-changed full-suite diff — same pre-existing flakiness class either way (see below), same single pre-existing `registration-form.test.ts` flake once file-parallelism is disabled, zero new failures.
- `server/wrangler.jsonc` gained a `hyperdrive` binding block with a placeholder `id` and a TODO comment — the user must run `wrangler hyperdrive create` themselves (a live-Cloudflare-resource step, deliberately not run by this change) and paste the resulting id in.

**`db`'s `Proxy` implementation detail worth knowing if you touch this file again:** the `get` trap must distinguish drizzle's own instance properties (e.g. `$client` — the raw postgres-js client, itself a callable tagged-template function with extra methods like `.end()`/`.begin()` attached) from inherited prototype methods (`select`/`insert`/`transaction`/etc., which need `this === <the real drizzle instance>`, not the Proxy). Blindly `.bind()`-ing every function-typed property (the first version of this fix) silently strips `$client`'s extra methods since `Function.prototype.bind` doesn't copy a function's own properties — broke every test's `afterAll(() => db.$client.end())` teardown. Fixed by checking `Object.prototype.hasOwnProperty.call(instance, prop)`: own properties are returned as-is (untouched), only inherited (prototype) methods get bound.

**Full-suite note (not new, but re-confirmed while verifying this change):** running the entire suite with default vitest file-parallelism against local Docker Postgres (`max_connections: 100`) intermittently throws `sorry, too many clients already` across many unrelated test files — reproduced identically on the pre-change baseline via `git stash`, so it's environmental flakiness from connection-pool exhaustion under parallel workers, not a correctness bug in any one change. `npx vitest run --no-file-parallelism` is the reliable way to get a clean signal locally when a run looks suspicious.

## SEO infrastructure (landed 2026-09-19)

**Standing rule, going forward: a new public-facing feature or page is not done until its SEO surface is wired up in the same change.** Concretely, for any new indexable/shareable page:
- Render a `<PageMeta>` (`web/src/components/seo/page-meta.tsx`) with a real `title`/`description`/`path`, not a copy-pasted placeholder. If the content has a natural `schema.org` type (an event, a product, an article, a list of things), pass it via `jsonLd` — the prop accepts one object or an array of them (added in this slice for `BreadcrumbList`/`ItemList` alongside the existing `Event`).
- Add the route to `server/routes/sitemap.ts`'s `STATIC_PAGES` if it's a fixed public page, or extend a `listPublic*` action the way `listPublicMunSlugs` (`lib/actions/marketplace.ts`) works if it's a dynamic per-record page.
- Add it to `DISALLOWED_WEB_PATHS` (same file) and `web/public/robots.txt` if it must stay out of search results (auth-gated, funnel, preview pages) — keep the two lists identical, there's a test for it.
- If the page is the kind of thing a person would actually paste into Instagram/WhatsApp/a group chat (i.e. it's not just crawled, it's *shared*) — a new per-record public page alongside `/mun/:slug` is the main case this would apply to — it also needs a non-JS path, not just client-side `PageMeta`. See the next section for why and how.

**Why `PageMeta`/`react-helmet-async` alone was never enough, and probably won't be for the next such page either.** It only rewrites `<head>` after React hydrates in a real browser. Link-unfurl bots (Instagram DM, WhatsApp, Facebook, Twitter/X, LinkedIn, Slack, Discord) and most search crawlers never run that JS — so every `/mun/:slug` link and every `<slug>.munhub.in` wildcard link showed the same generic site-wide card, regardless of what `PageMeta` rendered, until this slice. Lighthouse's SEO audit is *not* a way to catch this class of bug — Lighthouse drives a real headless Chrome that executes the JS, so it already scored 100/100 on `/`, `/muns` and `/mun/:slug` in production both before and after this change. The only real test is a bot-UA `curl` (see below) or actually pasting the link into the target app.

**The fix is split across two platforms, because production is split across two platforms** (see "Deploy config" above — `www.munhub.in`/apex is Vercel; `app./publish./admin./*.munhub.in` is the `munhub-web` Cloudflare Worker). Both share `web/src/lib/social-preview.ts` (`CRAWLER_USER_AGENT` bot-detection regex, `fetchMunForSocialPreview`, `buildSocialPreviewHead`/`buildSocialPreviewDocument`) so the emitted tags are identical either way:
- **Cloudflare (`munhub-web`):** `web/wrangler.jsonc` now has `main: "src/server/social-preview-worker.ts"` and `assets.run_worker_first: true` — the worker runs in front of the static build for every request. For a bot UA on `/mun/:slug` or a `*.munhub.in` wildcard host, it fetches the MUN, then rewrites the real asset response's `<head>` in place with Cloudflare's `HTMLRewriter` (removing the `data-default-seo` placeholders from `web/index.html`). Everything else is an untouched `env.ASSETS.fetch(request)` passthrough — no added latency for real users. Also proxies `/sitemap.xml` to the API with a real 200 (it used to be a 302, which is why `web/public/_redirects` no longer has that line).
- **Vercel (`www.munhub.in`):** `web/vercel.json` has a `rewrites` entry matching `/mun/:slug` with a `has` header condition (regex on `user-agent`, kept in sync with `CRAWLER_USER_AGENT` by hand — JSON can't import a TS constant) that routes only bot UAs to `web/api/social-preview.ts`, a plain Vercel Function (default Node.js runtime, no `config` export needed — see https://vercel.com/docs/functions/configuring-functions/runtime) which builds a complete standalone HTML document from scratch (bots never run the real JS bundle, so there's no need to graft onto the real `dist/index.html` here the way the Cloudflare side does). Also proxies `/sitemap.xml` the same way (a `rewrites` entry with an external `destination`, not a `redirects` entry).
- New ambient types for Cloudflare-only globals (`HTMLRewriter`, `Fetcher`) live in `web/src/server/cf-runtime.d.ts` rather than pulling in `@cloudflare/workers-types` — that package's own `Request`/`Response` types collide with `tsconfig.app.json`'s DOM lib. `web/api/**` gets its own `tsconfig.api.json` (no DOM lib, `types: ["node"]`, same `@/*` path alias as `tsconfig.app.json`) for the same reason, in reverse — added to `web/tsconfig.json`'s `references`.
- Verify locally: `wrangler dev` in `web/` + `curl -A "facebookexternalhit/1.1" http://127.0.0.1:<port>/mun/<real-slug>` should show the real MUN's tags; a normal browser UA should show the untouched generic default. Vercel's `has` header matching does **not** work under `vercel dev` (confirmed in Vercel's own docs) — test `web/api/social-preview.ts` directly instead (`GET(new Request(...))`) or via a real preview/production deploy.

**Sitemap image extension:** `listPublicMunSlugs` (`lib/actions/marketplace.ts`) now also returns each MUN's cover image URL; `server/routes/sitemap.ts`'s `buildSitemapXml` emits a `<image:image>` entry per MUN when one exists (Google Images indexing). `og-default.png` (`web/public/og-default.png`) is confirmed exactly 1200×630 — the Meta/Instagram/WhatsApp/Facebook crawler spec's recommended OG image size (1.91:1, min 600×315, <8MB) — keep any future default/fallback share image at that size.

**Not yet deployed.** All of the above landed in the working tree only (new `web/src/server/social-preview-worker.ts`, `web/api/social-preview.ts`, `web/src/lib/social-preview.ts`, `web/tsconfig.api.json`, `web/src/server/cf-runtime.d.ts`; edited `web/wrangler.jsonc`, `web/vercel.json`, `web/index.html`, `web/public/_redirects`, `web/src/components/seo/page-meta.tsx`, `web/src/pages/mun-detail-page.tsx`, `web/src/pages/muns-page.tsx`, `server/routes/sitemap.ts`, `lib/actions/marketplace.ts` + its test). Needs `wrangler deploy` for both `munhub-web` and `munhub-api` (the sitemap image-extension change touches the API too), and whatever the user's normal Vercel deploy path is (this repo has no `vercel.json` `git` block or CLI script committed, so it's presumably git-push-triggered — confirm before pushing, since the working tree also has an unrelated in-flight nav/logo redesign that shouldn't ship bundled with this if the user wants them separate).

## Payments: Cashfree (landed 2026-09-24, replaces GuruPay)

**Cashfree is now the live payment gateway. GuruPay (shipped 2026-09-18) was fully removed** — no GuruPay code, tests, docs (beyond a kept-as-historical-reference header note), env vars or CSP entries remain. Full reference doc: `docs/payments/CASHFREE.md` (mirrors `docs/payments/INTEGRATION.md`'s structure: how the seam works, the full API contract, environment table, go-live checklist). `docs/payments/SPEC.md` (GuruPay) and `docs/payments/INTEGRATION.md` (the never-built Razorpay recipe) are both kept, header-noted as superseded, for historical design-decision context only.

**Why the swap changed more than the provider name.** Cashfree's real API (confirmed via a live diagnostic `POST /pg/orders` call against `api.cashfree.com` before any code was written, same discipline `gurupay-adapter.ts`'s own history required after a first wrong assumption broke production) forced genuine architecture differences, not just a renamed adapter:
- **Real webhook signatures**, unlike GuruPay's check-status-only trust model: `x-webhook-signature` = base64(HMAC-SHA256(`x-webhook-timestamp` + rawBody, the **client secret** — there is no separate webhook secret to generate or configure)). `x-webhook-timestamp` is a genuine signed delivery time, so `lib/payments/webhook.ts`'s existing 5-minute replay window is a real defense for this provider, not a no-op. The reconciliation job (`lib/jobs/reconcile-cashfree-orders.ts`, `checkOrderPayments`/`GET /orders/{id}/payments`) is purely a missed-delivery safety net now, not the primary trust mechanism GuruPay's equivalent job was.
- **No plain redirect URL.** Cashfree's `create-order` returns `payment_session_id`, not a URL — checkout is SDK-driven: the browser loads `https://sdk.cashfree.com/js/v3/cashfree.js` and calls `cashfree.checkout({ paymentSessionId, redirectTarget: "_self" })`, which performs the actual browser redirect (`web/src/lib/cashfree.ts`, `web/src/components/registration/cashfree-checkout.tsx`). `lib/payments/adapter.ts`'s `PaymentOrder` gained `checkoutSessionId?: string` alongside the pre-existing `checkoutUrl?: string` (kept for schema/type continuity — historical GuruPay `payments.checkout_url` rows still have real values; no currently-shipped adapter sets it). New nullable `payments.checkout_session_id` column, migration `0040_true_enchantress.sql`.
- **`customer_details` (id/name/email/phone) is required** on order creation — GuruPay never needed this. `lib/actions/registration.ts`'s `loadCustomerDetails(userId)` looks up the paying user's `name`/`email`/`phone` from `users` immediately before both `createOrder` call sites (solo and group registration) and passes it via the new optional `CreateOrderInput.customer` field. `phone` is guaranteed set in real traffic (`isProfileComplete` already gates registration on it) but the function stays defensive since `initiateRegistration` itself is deliberately callable directly in tests without that gate.
- **Order id ≤45 chars, alphanumeric/underscore/hyphen.** GuruPay's `mh_<registrationId>_<uuid>` scheme (76 chars) didn't fit; Cashfree's adapter uses `mh_<uuid>` alone (39 chars) — no registrationId embedded, since `payments.provider_order_id` already links back to the registration in the DB, exactly as GuruPay's scheme never actually needed the embedded id parsed back out either.

**Fee model, webhook processor, registry pattern: all unchanged and reused as-is.** `lib/payments/fees-additive.ts`'s additive model (student pays listed price + fee + GST on the fee; organizer always gets the full listed price) is provider-agnostic and untouched. `lib/payments/webhook.ts`'s guarantees (signature-first, replay window, `(provider, eventId)` dedupe, row locks, amount/currency match, no-refunds-only-exceptions) are exactly the same code path Cashfree's `processPaymentWebhook`/`processNormalizedPaymentEvent` calls always did for GuruPay.

**Env vars:** `PAYMENTS_ADAPTER=cashfree`, `CASHFREE_CLIENT_ID`/`CASHFREE_CLIENT_SECRET` (secrets, `wrangler secret put`, never `process.env` — always `getRuntimeEnv`), `CASHFREE_ENV` (`production`/`sandbox`, default `production`), `VITE_CASHFREE_ENV` (web build var, must match). `PLATFORM_FEE_BPS`/`PLATFORM_FEE_TAX_BPS` unchanged (650/1800bps).

**Local secret handling:** the user supplied real production Cashfree credentials via a local `APIKey.csv` at the repo root — added to `.gitignore` immediately (it wasn't covered by the existing `.env*` pattern) since a bare secret file untracked at the repo root was one `git add -A` away from being committed. Values were moved into `server/.dev.vars` (gitignored, for `wrangler dev`) and, per the user's explicit choice to go all the way to a production cutover in the same session, into the `munhub-api` Cloudflare Worker's secrets via `wrangler secret put`.

## CI/CD: GitHub Actions now real, was previously documented but didn't exist (landed 2026-09-24)

`docs/operations/RUNBOOK.md` has described a "Deploy (production)" GitHub Actions workflow gated behind a required-reviewer `production` environment for a while — but `.github/workflows/` was completely empty until this change. It was aspirational documentation for a pipeline nobody had built. Two workflow files now exist and are real: `.github/workflows/ci.yml` and `.github/workflows/deploy.yml`. Full operational detail (secrets, one-time setup, the environment-name gotcha below) lives in RUNBOOK.md's "Deploying" section — this entry is the pointer + the trap a future agent would otherwise fall into.

- **`ci.yml`**: typecheck + lint + `npm run test:ci` on push to `main` and on PRs, against a `postgres:16-alpine` service container seeded to match `.env.test`'s `mun_hub_test` database (same isolation rule as local dev — see "Test/dev DB isolation" above).
- **`deploy.yml`**: manual `workflow_dispatch` only, three boolean toggle inputs (`run_migrations`/`deploy_api`/`deploy_web`, matching RUNBOOK.md's "untick the steps you don't need" language), gated on `environment: production`. Steps mirror RUNBOOK.md's fallback commands almost verbatim: typecheck, `npx tsx lib/db/migrate.ts` against Neon, `wrangler deploy --env="" --tag <sha>` for both `server/` and `web/`, then a health check against `https://api.munhub.in/api/v1/health`.
- **The environment-name trap:** GitHub already had an environment literally named `Production` (capital P, id `21808864398`) — auto-created by Vercel's GitHub integration for the `mun-hub` Vercel project (which deploys `munhub.in`/`www.munhub.in`, unrelated to these Worker deploys). GitHub matches a workflow's `environment:` reference **case-insensitively**, so `deploy.yml`'s lowercase `environment: production` silently resolves to that same pre-existing `Production` environment rather than creating a new one. There is no separate lowercase `production` environment and there shouldn't be — don't go looking for one or try to create a second.
- **Secrets, current state:** `CLOUDFLARE_ACCOUNT_ID` and `DATABASE_URL` are set on that environment (`DATABASE_URL` is Neon's pooled connection string, not the direct one RUNBOOK.md's setup calls for — proven working, flagged as a known deviation, swap it when convenient). **`CLOUDFLARE_API_TOKEN` is still missing** — the only credential a `wrangler login` OAuth session can't produce; it has to be a human-generated Cloudflare dashboard token with the scopes RUNBOOK.md lists, added via `gh secret set CLOUDFLARE_API_TOKEN --env production`. Until it's set, `deploy.yml`'s `wrangler deploy` steps will fail with an auth error if run — the workflow itself is complete, this is purely a missing-credential gap.
- If a deploy run fails, check RUNBOOK.md's updated "From GitHub Actions" section first, then this environment's secrets — not the workflow YAML, which was correct as of this landing.
